## Hurrican: the original developer's wording controls its own code

The [official developer page](https://www.winterworks.de/project/hurrican/) confirms Hurrican's source release and links the port lineage. This is developer-source evidence, not disassembly or an independently certified clean-room reconstruction. The modern tree's [release README](https://github.com/HurricanGame/Hurrican/blob/0d91d1f2d40f38d21e7f41afc01369ee55649fb6/README.txt) gives permission to modify/port/use the archive with a no-charge condition; it separately requires contact for commercial asset use. The later porter's MIT sentence applies to his original files while retaining original-file terms for edits. It does not establish a new unrestricted grant over all developer code or assets. The earlier fork's [license explanation](https://github.com/NebuPookins/hurrican/blob/dc23fa2a52939b2366dbaee3cfb5c965ef5fcb34/LICENSE.md) explicitly preserves that distinction. Independently replacing graphics does not remove the original-code condition.

Content is separate. The current [README](https://github.com/HurricanGame/Hurrican/blob/0d91d1f2d40f38d21e7f41afc01369ee55649fb6/README.md) mentions extra user levels, while the shipped [game readme](https://github.com/HurricanGame/Hurrican/blob/0d91d1f2d40f38d21e7f41afc01369ee55649fb6/Hurrican/readme.txt) describes freeware distribution constraints. Contributor maps, music, artwork, title/brand material and other game data are not CC0 just because source is visible. No full independent replacement pack was established; no media was fetched.

Dependencies differ between forks. The modern [CMake selection](https://github.com/HurricanGame/Hurrican/blob/0d91d1f2d40f38d21e7f41afc01369ee55649fb6/Hurrican/CMakeLists.txt) uses SDL/image/mixer, libepoxy, GLM, optional libopenmpt and selected renderer helpers. Its `SDL_fmod` [header](https://github.com/HurricanGame/Hurrican/blob/0d91d1f2d40f38d21e7f41afc01369ee55649fb6/Hurrican/src/SDLPort/SDL_fmod.hpp) includes SDL_mixer, with libopenmpt under an option; the companion implementation has its own MIT header. This does **not** prove a linked proprietary FMOD archive. The old fork's UnRAR library has dual GPL/custom terms, including restrictions in the custom option. Its presence is not proof that the newer CMake target links it. Exact selected dependency grants and emitted closure remain open.

GLES2/3 renderer choices improve potential portability, but the selected GL header still includes libepoxy and the [main loop](https://github.com/HurricanGame/Hurrican/blob/0d91d1f2d40f38d21e7f41afc01369ee55649fb6/Hurrican/src/Main.cpp) uses an ordinary blocking loop. No complete yielding Web target was established by these selected files. Reopening requires a suitable original-code grant or a user-accepted restricted route, separate complete content provenance/replacements, selected dependency closure, then silent Web adaptation and gameplay/save/Stop verification. No build was attempted after the eligibility gate failed.

## Hydra Castle Labyrinth: reported permission is GPL, not permissive

That is reported permission evidence; the underlying agreement and exact identity/scope of the referenced author were not independently authenticated. Do not turn it into either an MIT grant or a claim that all permission evidence is absent. It identifies the original game as E. Hashimoto/Buster's work and the port as fan-made; no matching decompilation claim is established.

Its [CMake](https://github.com/ptitSeb/hydracastlelabyrinth/blob/e31648688434a789e3056e52cdf1b9a842eeed48/CMakeLists.txt) has a concrete Emscripten selection using SDL2, mixer, Ogg/Vorbis and a preloaded `data` directory. That is stronger browser-path evidence than a library's generic Web support, but not our gameplay acceptance. The code route is GPL and outside the current permissive intake. The selected xBRZ directory also carries a GPLv3 notice, separate from the root GPLv2 notice; complete selected-version compatibility/closure is not resolved here. Default native SDL versions and the selected Web SDL2 branch must not be conflated.

No separately documented CC0 full campaign/presentation pack was established. A no-ROM browser executable can still depend on copyrighted game maps/graphics/audio. Reopening requires an accepted code route and exact author/component/content scope, then independent content where needed and silent gameplay verification. The hosted game was not opened.

## Spelunky Classic: official source availability with a no-sale condition

The [official Classic page](https://spelunkyworld.com/original.html) links developer source and the [Spelunky User License](https://www.spelunkyworld.com/files/COPYING.txt). The exact official license bytes match the selected mirror's [COPYING.txt](https://github.com/videogamepreservation/spelunky/blob/183a8382f58aec1d343cfc8af0e1d1474b0cf7f0/COPYING.txt). The web text reader initially failed to decode its non-UTF-8 trademark byte; a bounded raw-text fetch and Windows-1252 read succeeded. This is not a missing license endpoint.

That license explicitly covers the game, source .gmk files and modified versions, permitting modification/redistribution with notices and restrictions on sale. The restriction is on source-derived covered works as well as assets. Replacing sprites does not convert the original game code into MIT. The [source readme](https://github.com/videogamepreservation/spelunky/blob/183a8382f58aec1d343cfc8af0e1d1474b0cf7f0/readme.txt) also identifies GameMaker and additional platform/sound/scaling code. The .gmk files are not plain source-only Web build recipes; none was fetched or unpacked. A separate Unity fan project surfaced in discovery, but its own MIT code does not relicense Derek Yu's source/media and broad recreation expansion remains paused, so it was not imported as a substitute.
