## Three-course playable prototype

The [source experiment](../experiments/beacon-relay/README.md) supplies independent drawing commands, rover sprite animation, light/beacon graphics, square exhaust presentation, font glyphs, palette, text substitutions and three original maps. Gameplay and inherited procedural effect algorithms remain author MIT code; the own content dedication does not relicense those algorithms. The prototype deliberately has no audio implementation. It does not render every original object or reproduce the original campaign, PICO-8 hardware, timing/math behavior or commercial presentation.

The [ordinary browser gameplay receipt](beacon-relay-private-gameplay-2026-10-14.json) verifies all three courses, all three lights, native jump/dash consumption/recharge, a deliberate trench fall and native respawn, collision with each native flag object, and the visible **RELAY COMPLETE / THREE BEACONS LIT** overlay. A read-only observer recorded state; the accepted gameplay run used keyboard/buttons and supplied no player coordinate, score, object-state, RNG or completion setters. The own controller loads the next authored room only after the native goal collision and the Next course button.

Upstream `flag.init()` increments `PICO_COMPLETES` when the flag is instantiated. It is **not win evidence**. The own controller reads the private `flag.show` field set by the native player collision in `flag.draw()`. After a death/reload, the upstream statistic can increase again without another win. The receipt keeps those statistics visible without treating them as course completion.

The adapter holds brief key-down edges through one native tick, releases held input on focus loss, and runs a 30-tick/second loop. An initial test sent an instantaneous key press between ticks and did not start the title; it is retained/excluded. A separate test that copied checkpoint bytes between isolated browser contexts proved only decode/restore, not durable storage, and is also excluded from the durable claim. The accepted run saved the completed checkpoint normally, stopped the runtime, closed the full browser process, opened a new process with the same persistent profile, found byte-identical storage without copying it, and restored the completed relay.

The checkpoint stores only version and next-course index. Position, lights, retries and elapsed time are not durable fields. Final acceptance also retained an unfinished-course checkpoint across a full browser shutdown/new process and restored its entrance, verified a brief start tap, paused held-input suppression, and input release when canvas focus was lost while the direction key remained held. Separate storage fault injection rejected malformed/out-of-range checkpoints and simulated unavailable reads/writes. Save-failure feedback persists across subsequent frames after fixing the initial transient display. These storage guards deliberately modify browser storage, not native game state, and are labeled separately in the receipt. All test players were stopped, all browsers/servers closed, and all browser launches used `--mute-audio`. No audible audio test was performed.
